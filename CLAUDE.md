# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A WebXR `immersive-ar` app for Meta Quest 3. It runs in Meta Quest Browser and puts a small dig site (an excavator, its operator, a worker and some rocks, built from boxes, cylinders and spheres) at the centre of a table taken from the user's Space Setup. It's plain JS (ES modules, no TypeScript) with three.js 0.186 and Vite 8, and it needs Node 22.12 or newer.

## Commands

```bash
npm run dev                                   # HTTPS dev server on 0.0.0.0:5173 (strictPort), plus plain HTTP on :5174
npm test                                      # unit tests (node --test, auto-discovers test/*.test.js)
node --test --test-name-pattern="TableTracker"   # run matching unit tests only
npm run test:e2e                              # headless Chrome + Quest emulator, screenshots in e2e-output/
npm run build                                 # static site in dist/ (base './')
```

- **Tests:** there's no linter or formatter configured. `npm test` must stay `node --test` with no path: Node 22 treats a directory argument as a module and runs nothing.
- **Dev server:** `.claude/launch.json` has a `dev` config for the preview tool. The built-in browser pane rejects the self-signed HTTPS certificate, so use `http://localhost:5174/` there (localhost is a secure context, so the emulator and Enter AR work).
- **Seeing the headset:** in dev builds the Quest page reports console output, errors and app state to `logs/quest-debug.jsonl` (JSON lines; `kind` is `page`, `version`, `console`, `error` or `state`, and `device` says `Quest 3` vs `emulated Quest 3`). Read that file to find out what happened on the real device; there is no USB debugging. The `version` entry (and the "Updated …" line on the page and the in-AR menu) gives the newest mtime under `index.html` and `src/`, so check it to confirm the headset reloaded after a change.
- **Host names:** `server.allowedHosts` adds this PC's own name (`os.hostname()`, e.g. `aw8`, and `aw8.local`). Without it, Vite serves pages opened as `https://aw8:5173` but refuses their hot-reload websocket.
- **Config edits:** Vite restarts the dev server when `vite.config.js` or `scripts/vite-plugins.mjs` changes, but back-to-back edits can leave it on a stale config (one restart runs, the next is skipped). If a plugin change doesn't seem to apply, touch `vite.config.js` once more.
- **Windows Node:** Vite 8's bundler (Rolldown) ships only MSVC Windows binaries, so MinGW-built Node (MSYS2's `C:\msys64\mingw64\bin\node.exe`, which is first on PATH in the user's MSYS2 shell) crashes with "Cannot find native binding". Forcing the MSVC binding via `NAPI_RS_NATIVE_LIBRARY_PATH` isn't a fix: `vite build` then panics with "Node-API symbol has not been loaded". `scripts/check-node.mjs` runs as the `predev`/`prebuild`/`prepreview`/`pretest:e2e` hook and exits with an explanation instead. Use `C:\Program Files\nodejs`.
- **Quest access:** the headset loads `https://<pc-lan-ip>:5173/` over Wi-Fi and clicks through the self-signed certificate. WebXR needs a secure context, so plain HTTP over the LAN won't work. On this PC the Node firewall rules only allowed Public networks, so the Quest just spun until an inbound rule for TCP 5173 on the Private profile was added (see README).

## Architecture

- **`src/main.js`** is the entry point. In dev only (`import.meta.env.DEV`), and when a secure page lacks native `immersive-ar` (or `?emulate=1`), it dynamically imports `src/emulation.js` *before* importing `src/app.js`. Two things depend on that order: three captures `XRWebGLBinding` when the renderer is constructed, and IWER replaces `navigator.xr`. Keep emulation behind the `import.meta.env.DEV` check so `vite build` drops IWER entirely; check with `grep -ri iwer dist`.
- **`src/app.js`** (`initApp()`) owns the renderer, the session lifecycle, the per-frame loop and the UI states. It builds the dig site once per look (`digs`: `LOOK_NAMES` = diorama, plain; or just the `?style=` sketch in dev), all under the anchor and all precompiled and warmed up, so switching looks in AR compiles and uploads nothing; `dig` is the one shown and everything goes through it (`dig.site`, `dig.rocks`, `dig.setDrive`, …). `setLook()` moves the state across with `siteState()`/`applySiteState()`, keeps the spin, moves the sound (`sound.setEmitter`) and saves `localStorage` `tableCube.look`; the paint hue (`tableCube.paintHue`) is shared, each look keeping its own saturation and lightness. Each frame it runs `findTables` (planes first; meshes only if no table planes exist, since Quest reports every table both ways), then `TableTracker.update`, `placeSite`, `describeState` and `messageFor` for the status panel. In-AR state lives in the `run` object, which is reset on `sessionstart` and `sessionend`.
- **`src/tableLocator.js`** holds all the geometry and table-selection logic. It's pure, with no three.js or DOM, so it can be unit-tested. It works on column-major matrices exactly as `XRRigidTransform.matrix` gives them.
- **`src/digSite.js`** builds the dig site in three.js, using the numbers from the Excavator Blockout design canvas (design units, y up, front +Z where the worker faces; `SITE_UNIT` is 0.5 mm, so it's about 42 × 20 cm). `createDigSite()` returns the `site` group, the excavator's `paint` material, its `height`, and its footprint `radius`: a circle round the origin that holds every part *and* the contact shadows. `app.js` uses that radius to shrink the site on small tables (`SITE_FIT`); it's measured with the excavator at home. The excavator is two groups: `excavator`, the chassis on its wheels, which drives (`setDrive(state)` sets its position and heading in the model frame, swings `house` and rolls each wheel group by distance / radius, each side its own when turning), and `house` (body, cab, operator, arm), which swings about the chassis's centre. Its front, the bucket end, is local -X. The excavator's contact shadow is a child of `excavator`, the bucket's of `house`. For driving, `createDigSite()` also returns `home`, `bodyRadius` (the circle round the swing axis that holds the wheels, house and chassis shadow, not the arm), `workerHome`/`workerRadius` and `origin` (the site's origin in model coordinates), all in design units; `rocks` (a `Rocks`, src/rocks.js) gives the rocks' obstacle circles. The worker is a group with leg and arm groups pivoting at hip and shoulder; `setWorker(state, swing)` places him, turns his head and swings his limbs, and his shadow walks with him. `armPoints()`/`teeth()` give model-frame points along the arm (elbow to teeth) for the joints' current angles (they walk the local matrices up to `model`, so they're right before rendering). The arm is a joint chain (`boomJoint` → `armJoint` → `bucket`, each turning about Z at its pin). `DIG_KEYS`/`digPose(t)` give eased joint angles for the 6 s dig cycle, its phase, and a 0–1 `hydraulics` speed; `animate(t, dig)` poses the arm at dig time `dig` and the operator's and worker's heads at clock time `t`; app.js advances `run.digTime` only while A is held, so the arm stops where it is when A is let go. The footprint radius and height are measured over 48 poses of the cycle, and `armLowest` is the arm's lowest point over it; the unit test requires it above the table (the scoop keys were lowered until the teeth clear the table by about 3.6 mm). `createDigSite({ shadowTexture: null })` builds without a DOM, which is how test/digSite.test.js runs it in node. `createDigSite({ style })` builds every part through a look from src/styles.js (default `plain`), and also returns `marks` (src/groundMarks.js) and `wheels` (for the tracks).
- **`src/siteSound.js`** (`SiteSound`) makes the sound with WebAudio, no files: a low-passed sawtooth diesel hum with a 7.5 Hz chug, band-passed noise hiss and a 470 Hz whine scaled by `hydraulics` (app.js passes the work load: the dig speed while digging, or driving/turning/swinging, `driveLoad`), and a burst of short noise grains (rock clatter) when the phase becomes `scoop` or `dump`. It's a `THREE.PositionalAudio` on the excavator, with the `AudioListener` on the camera. `start()` must run inside the Enter AR click (browsers block audio otherwise), and `stop()` suspends the context when AR ends. Sound is off by default (`localStorage` `tableCube.soundMuted` must be `'0'` to start on); the menu's third button toggles it. The graph still runs at zero gain while off, so turning it on from an XR select doesn't need a user activation; e2e runs Chrome with `--autoplay-policy=no-user-gesture-required` so the context actually runs there.
- **`src/controllerInput.js`** reads the Touch controllers (`readLeftStick`, `readRightController` with A and B, `deflection`, `viewerHeading`); holding B cycles the excavator's paint hue in sRGB (`nextHue`, `repaint` in app.js). It's pure, like `tableLocator.js`.
- **`src/excavatorDrive.js`** (pure) turns the sticks into motion, in the site's model frame (design units; heading h faces (-cos h, sin h)). `stepDrive(state, input, world, dt)`: the left stick drives, only ever along the heading, with speed and turn rate ramped (`DRIVE_ACCEL`/`DRIVE_BRAKE`/`TURN_ACCEL`); `relative` steering is forward/back + turn on the spot (right = clockwise), `absolute` turns towards the stick's direction as the user sees it (`viewHeading`, the viewer heading turned into the site frame by the table yaw + site spin) and drives forwards, slowing by cos(error). The right stick's x swings the house. A move that would put the body circle off the table (`area`: the table top in the site frame, turned by the site's spin, in units at the site's scale; `driveArea` in app.js) or into an obstacle (the resting rocks and the worker: `siteObstacles()` in app.js) stops where it touches (binary search along the heading, speed 0), never sliding sideways; `settle` pulls a position that no longer fits (the outline changed) back in. The arm may reach past the edge. `travel` adds up the distance for the wheels. app.js keeps the state in `run.drive` and calls `setDrive`; a newly locked table without a dig site of its own (see placementMemory below) starts the site as built (`resetSite()`: excavator parked, arm at rest, rocks in their pile, worker at home); the site itself always sits at the table centre, its spin set by `quarterTurnToward` so it faces the user while staying square to the table. Steering is `localStorage` `tableCube.steering` (`relative` default, `absolute`), switched by the menu's Steering button and logged as `[drive] steering: …`.
- **`src/rocks.js`** (`Rocks`, three.js; pure helpers `restBase`, `rockToScoop`) moves the five rocks one by one, each with its own contact shadow (`SHADOW_SCALE`). app.js (`moveRocks`) watches the dig phase: entering `scoop` calls `scoop(teeth())`, which takes the highest resting rock within `SCOOP_REACH` of the teeth (rocks it held up fall); during `scoop`, `carry(progress)` slides it from where it lay to the bucket's inside in the model frame, lifting it so its lowest corner never goes under the table (attached rigidly it dipped 8.6 mm), and attaches it to the bucket at 1 (also forced when the phase leaves `scoop`); entering `return` calls `dump(area)`, which detaches it and lets it fall (gravity) onto the highest resting rock under it or the table, kept on the table by `area.contains` (excavatorDrive's `settle`). Rocks sit `SINK` (2 units) into what they rest on. `state()`/`restore()`/`reset()` (de)serialise them (model-frame position + quaternion, or `carried`). From home the teeth reach two rocks, and without a swing the dump lands back over the pile: the gameplay is scoop, let go of A at `lift`, swing or drive, hold A to dump. A and the right stick are both under the right thumb, which is why letting go of A freezes the arm.
- **`src/worker.js`** (pure) is the worker's behaviour, in the model frame: `stepWorker(state, { threats, watch, radius, area, obstacles }, dt)`. Threats are circles: the arm points below `WORKER_HEIGHT` (260 units, app.js) and the excavator's body, now and `predictPoints`-ed at `LOOKAHEADS_S` (0.4/0.8/1.2 s) by the swing, turning and driving rates, so his escape spot (`escapeSpot`: straight away, else rotated alternatives, `settle`d onto the table, out of rocks and the machine) is clear of the whole sweep. Closer than `SAFE_GAP` he walks there (`RUN_SPEED` when under half of it); otherwise he turns his head (up to 1.1 rad) and, beyond that, his body to watch the excavator. `limbSwing` gives the walk's limb swing. With a single 0.7 s lookahead he lost the race against a full-speed swing.
- **`src/placementMemory.js`** (`PlacementMemory`) keeps a dig site per table. Each site is a persistent anchor (`frame.createAnchor` at the site's base, turned by the site's world yaw; `requestPersistentHandle`) plus its state, app.js's `siteState()` (excavator x/z/heading/swing/digTime, rocks, worker); `localStorage` `tableCube.placement` = `{ v: 2, current: uuid, sites: [{ anchor, savedAt, usedAt, state }] }` (v1, a single site, is read too). `current` (the `home` site: the last one the user worked on) is where the site goes next session. `start(session)` restores every saved site whose anchor `session.persistentAnchors` still has; `locate()` updates their poses each frame and reports `pending` until home's pose is known or `RESTORE_TIMEOUT_MS` (4 s) passes, and app.js doesn't place the site meanwhile. Then app.js (`findRemembered`) locks the table under home with `tracker.lockTo(…, 'remembered')`, which beats provisional picks but never a user's choice. On every lock change app.js asks `siteFor(site base)` (`nearestSite`: 30 cm across, 10 cm in height): the current site (its table only dropped out, e.g. the headset was off) keeps the state in hand; another site with a state is `select`ed (which saves the one being left first), turned by `snapQuarterTurn(site yaw - table yaw)` and applied; otherwise `select(null)` and `resetSite()`. `keep()` runs every frame while the lock is firm: it makes the current site if there's none (adopting one whose anchor turned up late, rather than doubling it), makes it home, re-anchors it when it moved over 5 cm or 0.05 rad (deleting its old anchor) and saves at most once a second (only when something changed). Over `MAX_SITES` (6; Quest keeps 8 per site) the one used longest ago is forgotten and its anchor deleted. `flush()` runs on sessionend, visibility `hidden` and `pagehide`. Without the `anchors` feature, sites live only in the session (by their kept pose). Reset on the menu (`resetSite()`) starts the current table afresh. Paint is `tableCube.paintHue`, one for all tables, saved when B is released. Logs `[memory] …`.
- **`src/styles.js`** (`makeLook(name)`, `STYLES`) holds the looks: per part role (`paint`, `tyre`, `metal`, `dark`, `skin`, `hat`, `eye`, `cloth`, `rock`; digSite's `ROLES` maps its colours) a material, geometry makers for boxes, cylinders, spheres and rocks, a shadow tweak, `decorate(ctx)` for extras added after the measuring, and `marks` (show ground marks). `diorama` (the default) is earthy and flat-shaded with faceted rocks, on a ragged dirt disc with a mound under the pile, clods (kept off `ctx.clear`: the excavator, the worker, the pile) and grass round the rim; all of it is `userData.ground` and has a flat bottom at y = -0.5 (the site's base is 1 mm above the table, the shadows sit at y = 1), so nothing goes under the table (a unit test checks every vertex). `plain` is the original look. `toy`, `wood`, `cartoon` (toon shading, back-face outlines), `hologram` (edges, grid) and `clay` (lumpy geometry) are sketches, only reachable with `?style=`. Built-in three materials keep the occlusion hook (`#include <dithering_fragment>`); lines need `occlusion.apply` too (app.js does it for `isLine`).
- **`src/groundMarks.js`** draws what the site leaves on the table: `GroundMarks` is one `InstancedMesh` of flat marks with a fixed number of slots (all drawn, unused ones scaled to nothing, so nothing is uploaded or recompiled in AR; `frustumCulled` off; `renderOrder` -1; polygon offset over the ground), oldest replaced first, with `state()`/`restore()`. `tracks` (alpha-tested tread, `TRACK_CAPACITY` 400) get a mark per wheel row at its trailing wheel every `TRACK_STEP` (30 units) of that row's own rolling (`treadMarks`, pure: the same per-side distance setDrive turns the wheels by, so turning on the spot leaves marks too); `spills` (soft blobs, tinted darker by `tone`) get a dug patch where a scoop starts (if the teeth are over the table) and dirt under every rock that lands (`Rocks.update` returns them). Marks exist in every look (so switching keeps them) but show only where the look has `marks`; they're part of `siteState()` and so of each table's saved site.
- **`src/debugChannel.js`** (dev only, loaded first by `main.js`, `?debug=0` disables) wraps `console.*` and window error events, samples `app.snapshot()` every second, and POSTs batches to `/__debug` every 2 s. A state entry goes out on any visible change and every 10 s while presenting. `scripts/vite-plugins.mjs` has the server side (`debugLog`, which appends to the log file and echoes page errors in the terminal) and `plainHttp`, an HTTP mirror of the dev server's middleware that hands websocket upgrades to Vite so hot reload works over HTTP. In `e2e` mode (used by `scripts/e2e.mjs`) `vite.config.js` drops the HTTP mirror and writes the debug log to `e2e-output/debug-log.jsonl`, which the e2e scenarios read (`waitForDebugLog`) to check `[tables]` and `[menu]` lines. On `pagehide` the channel sends what's queued with `sendBeacon`, so a reload's last lines (e.g. `[menu] reload pressed`) still arrive.
- **`src/xrMenu.js`** is the in-AR menu: Exit AR, ↻ Reload, Sound on/off; Steering relative/absolute and ↺ Reset; Look (a third row); labels via `setLabel`, and the "Updated …" line. The panel (background, version line) and each button have their own canvas texture (the buttons are meshes 0.5 mm in front, `renderOrder` 1), so a hover or label change uploads only that button; with one big canvas, pressing Steering cost a 21.8 ms frame on the Quest. It floats above the left controller's grip pose (or the left hand's wrist joint) and faces the user. The other hand's target ray is raycast into it every frame, which highlights the hovered button and shows a ray. `onSelect` in `app.js` asks `menu.buttonFor(event.frame, event.inputSource, …)` first, so a trigger or pinch on a button presses it instead of switching tables. `buttonAt(u, v)` is the pure hit test. `src/version.js` fetches `./__version.json`, which the `siteVersion` plugin in `scripts/vite-plugins.mjs` serves live in dev and writes into `dist/` on build.
- **`src/statusPanel.js`** draws the in-headset text panel on a canvas. Quest has no `dom-overlay`. The canvas has one fixed size (768 px wide, room for 5 body lines) and the text box is drawn centred in it, so a text change only re-uploads the texture in place (`needsUpdate`); three allocates immutable texture storage, so a size change would mean a new texture. There are no mipmaps on the panel or menu textures (always seen up close), because rebuilding them on every change cost time on the Quest.
- **`src/occlusion.js`** (`SoftOcclusion`) hides the dig site behind real things using the depth map (see Occlusion below). app.js applies it to every site material and calls `update(view)` each frame before rendering.
- **`src/emulation.js`** sets up IWER and `@iwer/sem` synthetic rooms, and marks IWER's depth encoding (`encodedDepthFar`). The `?env=` and `?planes=1` query params apply only on the dev server.
- **`scripts/e2e.mjs`** starts Vite programmatically (port 5199), drives Chrome over raw CDP with Node's global `WebSocket`, and uses the dev-only hooks `window.__app` (`startAR`, `endAR`, `selectNext`, `setOcclusion`, `snapshot()`; `snapshot().look` and `.marks` (track and spill counts); `snapshot().excavator` has its room position and forward, table-frame position and limits, `clearance` to the obstacles, `atHome`, `digTime`, `steering`) and `window.__iwer.xrDevice`. Its expected table coordinates come from the `@iwer/sem` capture files for `meeting_room` and `living_room`. `E2E_ONLY=<text>` runs only scenarios whose names contain it. `openApp` clears the origin's localStorage (CDP `Storage.clearDataForOrigin`, after leaving the page so an unloading page can't save again) unless `{ remember: true }`: the remembered dig site, steering and paint would otherwise leak between scenarios. The depth scenario counts the site's coloured pixels with occlusion on and off (`shownFraction`): from just below the table top, the table's edge must hide part of it, and from above, none of it.

## WebXR and Quest facts the code depends on

These were verified against specs, package source and a real Quest 3. Don't "simplify" them away:

- **Plane normal sign.** The sign of planeSpace +Y isn't fixed by the spec, and on Quest/IWER table planes it points down. Never offset along the plane normal or copy the plane's full rotation. Lift along reference-space +Y and take yaw only (`yawFromMatrix`).
- **Plane polygons.** They are closed loops on Quest/IWER (the first vertex repeated), so use the area-weighted centroid, not a vertex average.
- **Table meshes.** In IWER they are Z-up boxes with the origin at the top face. Measure in reference space (`tableTopFromMesh`).
- **Labels.** Accept `table` and the legacy `desk`, case-insensitive, possibly comma-separated.
- **Lock identity.** XRPlane/XRMesh objects keep their identity across frames while they're reported, so `TableTracker` locks by object identity. But a plane that drops out and comes back is a new object (seen in IWER; Chromium works the same way), and on the Quest a table dropped out for a frame early in a session. So a missing locked table keeps its lock, and the site stays at its last known place, for `DROPOUT_GRACE_MS` (1 s; `update()` needs the frame time for that). A table back in the same place (`sameTable`: centres within 15 cm, 10 cm in height) takes over the lock. app.js watches `tracker.lockId`, which changes only on a genuine new pick, not on that takeover, so a dropout doesn't re-park the excavator. The provisional re-pick fires only for keys never seen before, not for tables that blink. Cycling order is anchored to where the viewer stood when the lock was made (`origin`), not to their current position. All plane/mesh references are invalid after the session ends.
- **Tables arrive late.** On a real Quest the room's planes arrive over the first frames, sometimes the far ones (another room, ~9.5 m away) first. So `pickTable` (distance + `OUT_OF_VIEW_PENALTY` 1.5 m when out of view) is provisional: `TableTracker` re-picks whenever the set of table keys changes, until `next()` (trigger/pinch) or `confirm()` (app.js calls it when the excavator drives, turns or swings, or while A digs). `tracker.reason` says why the lock was made, and app.js logs each lock change as `[tables] <reason>: table k of n, d m away`, and each ridden-out dropout (`tracker.takeRecovery()`) as `[tables] table back after N ms[ as a new object in the same place]; the site stayed put`. IWER delivers every plane on frame 1, so the e2e scenario hides tables by removing their native entities from `sem.trackedPlanes`/`trackedMeshes` and adds the same entities back.
- **No `ARButton`.** three's `ARButton` forces the `local` reference space. The app uses its own button, probes `local-floor`, and calls `setReferenceSpaceType` before `setSession`.
- **Optional features.** All scene features (`local-floor`, `plane-detection`, `mesh-detection`, `hand-tracking`, `depth-sensing`, `anchors`) are optional so that a denied permission doesn't block AR. Use `session.enabledFeatures` to explain what's missing. IWER rejects `requestReferenceSpace('local-floor')` unless it was requested.
- **Room capture.** `initiateRoomCapture()` works once per session, needs `plane-detection`, and doesn't exist in IWER, so feature-detect it.
- **Scene data timing.** On a real Quest it can take 2–3 s to arrive (`SCAN_GRACE_MS`). Under IWER it's there from the first frame, and IWER bumps `lastChangedTime` every frame.
- **Controller layout.** Quest Touch controllers use the `xr-standard` gamepad layout: on both controllers `axes[2]`/`axes[3]` are the thumbstick, and its y is negative when pushed forward (`axes[0]`/`axes[1]` are always-0 touchpad placeholders). `buttons[4]` is A on the right controller and X on the left. In IWER, drive them with `controllers.left`/`controllers.right` `.updateAxes('thumbstick', x, y)` and `updateButtonValue('a-button', 1)`.
- **Shaders are compiled before AR.** `precompile()` in app.js runs `renderer.compileAsync(scene, camera)` (it includes hidden objects) and `initTexture` for every `material.map` while the 2D page is up, and Enter AR stays disabled until it's done. Without it the Quest's first AR second had a 70-90 ms frame. It works because AR renders with the same program parameters: three r186 has no multiview, and the XR render target uses `renderer.outputColorSpace` and the renderer's tone mapping. If you add materials or objects later (after `initApp`), compile them too, or they'll stall their first frame. The occlusion code goes into the dig site's materials (`occlusion.apply`) before precompiling, and three's own depth pass, which would build its ShaderMaterial and plane in AR, is switched off (see Occlusion below). `snapshot().programs` (`renderer.info.programs.length`) must not grow after entering AR; the meeting-room e2e scenario checks that. Quest Browser lacks `KHR_parallel_shader_compile`, so `precompile()` calls `compileAsync` only when `renderer.extensions.has()` reports it (`get()` would log a warning on every load) and plain `compile()` otherwise.
- **Startup frames.** Precompiling didn't remove the stall in the first second of AR on the Quest (an 88 ms frame remained). `src/frameTrace.js` (`FrameTrace`, pure) records each frame's gap and the app's own time (`onXRFrame` vs `renderer.render`) for the first 3 s of a session, and app.js logs it as one `[startup] …` line. A long gap with little app time is the browser entering AR; long app or render time is ours. On the Quest it showed both: 38-63 ms browser gaps (unfixable), and a 35-46 ms render the first time the dig site appeared in a freshly loaded page (geometry upload). `warmUpDraw()` (called by `precompile()`) fixes the second by rendering the whole scene once, everything visible and nothing culled, into a 1x1 scissor box of the page canvas, which is then cleared. `snapshot().geometries` (`renderer.info.memory.geometries`) must not grow after entering AR; the meeting-room e2e scenario checks it. The session's `visibilityState` is in snapshots (`xrVisibility`) and changes are logged as `[session] visibility: …` (`hidden` usually means the headset was taken off).
- **Occlusion.** The session asks for `depth-sensing` (optional, `usagePreference: ['gpu-optimized']`, empty `dataFormatPreference` as in three's own example); Quest needs the Spatial permission for it. three would occlude by itself, writing the depth texture straight into the depth buffer (WebXRDepthSensing), but on the Quest that was blocky round hands and hid the rubble's bottom and the contact shadows where the table's depth is noisy. So `SoftOcclusion` (src/occlusion.js) sets `renderer.xr.getDepthSensingMesh = () => null` (three still updates the depth texture) and patches the dig site's materials via `onBeforeCompile`: 9 taps 1.5 texels apart, hidden only by a real surface 2–5 cm nearer (`DEFAULT_TOLERANCE`), alpha (opaque materials use `alphaToCoverage`, so MSAA does the soft edge without sorting). The tolerance is per material (`apply(material, { tolerance })`, a per-material uniform on the shared program): things lying flat on the table (`userData.ground`: the diorama's dirt and grass, the marks) use `GROUND_TOLERANCE` (1–2.2 cm), because with the default a controller lying on the desk (3 cm thick) was only a third hidden and the dirt painted over it; the flat things can't rise above the table's depth noise anyway. In dev, `window.__iwer.addProp({ at, size })` (src/emulation.js) puts a box into IWER's room so it shows in the depth map, which the e2e uses for this. Both depths are compared in metres. The depth texture holds depth-buffer values for the depth information's `depthNear`/`depthFar` (three's pass relies on that too), and those change in the first frames as three pushes the camera's near/far into the render state (IWER: 0.1/1000 on frame 1, then 0.01/20), so `update(view)` reads `getDepthInformation` every frame. IWER encodes `1 - near/z` (infinite far) whatever far it reports, so src/emulation.js gives its `XRWebGLDepthInformation` an `encodedDepthFar = Infinity` that occlusion.js prefers; decoding with the reported far made real surfaces a few cm too near. `[depth] depth map: …` logs the values whenever they change. The Quest 3 reports a 320x320 `texture-array` (format `unsigned-short`), near 0.1 m, far infinite, from the first frame, so three sets the XR camera's far to Infinity and the infinite-far decode applies (no errors, 90 fps). IWER renders depth from the SEM room mesh *and* the furniture boxes, and its scanned table top is 3–6 cm below the table plane. `?occlusion=debug` (dev) colours the site by depth instead.
- **Anchors in IWER.** IWER keeps persistent anchors in its own `localStorage` key, relative to a fixed global space, so they survive sessions and reloads; `restorePersistentAnchor` resolves on the next frame. Its `deletePersistentAnchor` drops the anchor from the session but not from that storage, so deleted ones come back after a reload (harmless: the app only looks for its own UUID). Never bulk-delete `session.persistentAnchors`: on a shared origin (GitHub Pages, say) they can belong to other apps.
- **Passthrough.** It needs `scene.background` to stay null; three clears to transparent in `alpha-blend`.
- **IWER setup.** It needs `installRuntime({ forceInstall: true })` on desktop Chrome, and `installSEM(SyntheticEnvironmentModule)` takes the class, not an instance; the package README's API name is stale. IWER only produces frames in a visible, non-zero-size viewport.
